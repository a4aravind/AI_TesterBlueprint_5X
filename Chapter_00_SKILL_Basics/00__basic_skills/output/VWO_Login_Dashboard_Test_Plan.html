1. Objective

Verify that users can securely and reliably access the VWO platform through a usable, responsive, accessible login experience. Validate the sign-in, session, recovery, and applicable enterprise authentication journeys against the supplied PRD, including error handling, integrations, performance objectives, and security controls.

Testing will also assess the PRD's stated success measures: 95% or higher login success rate, login-page load time under 2 seconds on standard connections, and 90% or higher user satisfaction. Measurement definitions and instrumentation must be agreed before these measures can be evaluated.

2. Scope

In scope

  • Email and password login, input validation, loading and success/error feedback.
  • Remember-me behavior, session creation, timeout, secure handling, and logout/session invalidation where available in the delivered product.
  • Password requirements and the forgot-password / email-based recovery journey.
  • Optional 2FA, organizational SSO (including configured SAML/OAuth flows), and social identity providers only where included in the release.
  • Responsive behavior, keyboard operation, screen-reader support, contrast, clickable labels, and light/dark themes where available.
  • Registration/free-trial path, support entry points, dashboard transition, and preservation of relevant pre-login navigation context where specified.
  • HTTPS, authentication data protection, rate limiting, privacy/compliance behaviors, analytics events, and applicable audit requirements.
  • Page performance, availability/load behavior, browser/device compatibility, and regression coverage.

Out of scope unless separately approved

  • Testing the internal functionality of the VWO experimentation, personalization, and analytics platform beyond login handoff and session access.
  • Biometric authentication, adaptive authentication, and progressive web app capabilities listed as future enhancements.
  • Unspecified onboarding features after registration, and third-party provider behavior outside the integration boundary.
  • Production penetration, brute-force, or load testing. Such testing requires explicit authorization and a designated environment.

5. Defect reporting procedure

  1. Record each issue in the project-approved defect tracker (tool TBD) with a concise title, environment/build, preconditions, reproducible steps, expected and actual results, impact, and priority/severity.
  2. Attach only sanitized screenshots, logs, and network evidence. Redact email addresses, credentials, cookies, session identifiers, reset links/tokens, and other personal or secret data.
  3. Classify security or privacy findings through the approved restricted reporting channel; do not include exploit payloads or sensitive data in broadly visible tickets.
  4. Triage with product, engineering, and QA; assign an owner and disposition. Retest the fix in the target environment and run focused regression around the affected journey.
  5. Share execution and defect status with stakeholders at the agreed cadence. The PRD/template does not provide named contacts, severity definitions, or reporting cadence; these are TBD.

6. Test strategy

  1. Requirement analysis: Map the PRD's functional and non-functional requirements to scenarios; resolve TBD items and confirm which optional capabilities ship.
  2. Test design: Apply equivalence partitioning and boundary-value analysis to fields and policy limits; decision tables to combinations of credentials, remember-me, MFA, and provider outcomes; state-transition testing to login, reset, challenge, and session states; use-case testing to new/returning-user flows. Use risk-based error guessing and exploratory testing for usability and recovery gaps.
  3. Smoke testing: On each candidate build, verify the login page renders and a core successful login plus a representative failure behaves correctly. Block deeper execution if the smoke test fails.
  4. Functional and integration testing: Execute prioritized scenarios for authentication, recovery, session handling, redirects, support/registration links, analytics, and any in-scope identity integrations.
  5. Non-functional testing: Validate accessibility, responsive behavior, supported-browser compatibility, performance, availability, and authorized security controls. Use approved test environments for security and load checks.
  6. Regression and retesting: Retest fixes and rerun affected P0/P1 flows; execute the agreed core-login regression set before release.
  7. Evidence and reporting: Track requirements, cases, results, defects, and metric measurements. Report gaps where a requirement is not measurable or evidence is unavailable.

9. Entry and exit criteria

Requirement analysis

Entry: PRD and available design/technical information are received.

Exit: Scope is reviewed; questions affecting testability, release scope, environments, and acceptance criteria are documented and either resolved or explicitly accepted as risks.

Test design

Entry: Requirements are sufficiently stable to derive scenarios.

Exit: Prioritized scenarios, test data needs, coverage traceability, and environment needs are reviewed by designated stakeholders. Sign-off owner is TBD.

Test execution

Entry: A testable build and authorized environment are available; access and test identities work; core requirements and cases are reviewed; smoke testing passes.

Exit: Planned in-scope tests have a recorded result or documented blocker/deviation; P0 defects are resolved or explicitly dispositioned; P1 risks and residual issues are communicated; required evidence and defect records are available.

Test closure

Entry: Execution results, defect status, and metric evidence (where measurable) are ready.

Exit: Test summary and residual-risk recommendation are shared; release acceptance and approval are recorded by designated owners. Owners and thresholds are TBD.

10. Test execution and closure

Run a smoke check for each candidate build, then execute prioritized functional and integration scenarios followed by applicable accessibility, compatibility, security, and performance coverage. Record pass, fail, blocked, or not-run status with evidence. Re-test fixes and repeat the affected regression set. The test lead should publish progress and escalate release-blocking issues using the project-agreed channel and cadence.

Testing is complete when the exit criteria above are met or any exception is documented and accepted by the authorized release stakeholders. The PRD does not define numerical release thresholds for open defects or pass rate; these must be agreed before closure.
